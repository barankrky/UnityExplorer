# UnityExplorer MCP

This document covers the built-in MCP (Model Context Protocol) server in UnityExplorer: architecture, setup, client configuration, the tool set, security switches, runtime limits, and troubleshooting. For the threat model and security rationale, see [MCP_SECURITY.md](MCP_SECURITY.md).

> MCP lets an external agent drive the running game. Validate on an offline, recoverable test save first, and never grant write access for untrusted games, servers, or MCP clients.

## 1. Architecture

```text
MCP client / Agent
        | SSE or Streamable HTTP (JSON-RPC 2.0)
        v
UnityExplorer DLL built-in MCP server  --  request queue  --  Unity main-thread pump
        |
        +-- scenes, GameObjects, Components, Transforms
        +-- reflection field/property reads and gated writes, method invocation
```

The MCP server, protocol handling, and game capability executor all live inside the UnityExplorer DLL. No Node.js, stdio adapter, or external forwarding process is required.

Layer responsibilities:

- **MCP client**: calls the standard methods `initialize`, `tools/list`, and `tools/call`, and is responsible for presenting tool approval to the user.
- **DLL built-in MCP server**: binds to loopback only, handles MCP sessions and JSON-RPC, validates the token, request size, queue capacity, and security mode, then queues the request.
- **Unity main-thread executor**: drains the queue from the Unity `Update` loop. All UnityEngine object access, scene operations, and reflection calls happen here, never on a network worker thread.
- **MCP UI panel**: configures enable/disable, transport mode, port, token, read-only mode, and the dangerous-operations switch; shows listening status, the last error, the connection endpoint, and copyable client configuration.

Transport modes:

- **SSE**: for clients using the legacy HTTP+SSE MCP transport. The client opens an event stream to the MCP endpoint and posts requests to the message endpoint the server advertises.
- **Streamable HTTP**: standard HTTP requests against the same MCP endpoint. This implementation is stateless: JSON-RPC requests return JSON directly, notifications return `202 Accepted`, and no `Mcp-Session-Id` is issued.

Both modes use JSON-RPC 2.0, and exactly one mode is active at a time. After switching modes, stop and restart the server before reconnecting clients. Object handles are only valid for the current process and scene; after a scene change, object destruction, or domain reload, clients must re-query objects rather than reuse stale handles.

## 2. Requirements and startup

1. Install and start a UnityExplorer DLL build that includes MCP support, as you would normally.
2. Open the **MCP panel** and pick the transport mode:
   - choose **SSE** if the client says `SSE`;
   - choose **Streamable HTTP** if the client says `Streamable HTTP`, `HTTP`, or is a newer remote-MCP client.
3. On first use, keep:
   - bind address `127.0.0.1`;
   - **read-only mode on**;
   - **dangerous operations off**;
   - a high-entropy token generated by the panel;
   - the default port and path, e.g. `http://127.0.0.1:17891/mcp`.
4. Start the server. If you change the transport mode, port, path, or token, restart the server before reconnecting the client.
5. Enter the URL and auth header shown in the panel directly into your MCP client. **No Node.js, stdio adapter, or external forwarder is needed.**

Do not commit a real token to Git, chat logs, screenshots, or public logs. Client requests use:

```http
Authorization: Bearer REPLACE_WITH_TOKEN_FROM_THE_MCP_PANEL
```

## 3. Configuring an MCP client

Prefer the panel's **Copy config** output, since it reflects the current transport mode, port, path, and token. The examples below assume `http://127.0.0.1:17891/mcp`.

### 3.1 SSE

Select **SSE** in the MCP panel, start or restart the server, then add the URL to your client configuration:

```json
{
  "mcpServers": {
    "unity-explorer": {
      "type": "sse",
      "url": "http://127.0.0.1:17891/mcp",
      "headers": {
        "Authorization": "Bearer REPLACE_WITH_TOKEN_FROM_THE_MCP_PANEL"
      }
    }
  }
}
```

If your client logs `sse type`, the panel must also be set to **SSE**. On a successful connection, `GET /mcp` returns `200 OK` with `Content-Type: text/event-stream`, not `405 Method Not Allowed`.

### 3.2 Streamable HTTP

Select **Streamable HTTP** in the panel, restart the server, and select the matching transport type in your client:

```json
{
  "mcpServers": {
    "unity-explorer": {
      "type": "streamableHttp",
      "url": "http://127.0.0.1:17891/mcp",
      "headers": {
        "Authorization": "Bearer REPLACE_WITH_TOKEN_FROM_THE_MCP_PANEL"
      }
    }
  }
}
```

Some client versions persist the transport type from their own UI instead of accepting a hand-written `type`. In that case, choose **Streamable HTTP** in the client's "add MCP" dialog and enter only the URL and headers; the panel's copy output remains authoritative.

This is the protocol-permitted stateless form of Streamable HTTP: `POST /mcp` handles requests, while `GET /mcp` and `DELETE /mcp` return `405`. The initialize response may omit `Mcp-Session-Id`, and clients must not treat that as a connection failure.

### 3.3 Switching transports

Stop the server, change **SSE / Streamable HTTP** in the panel, start the server again, then reconnect the client with the matching transport. A mismatch typically shows up as HTTP `405`, an immediately closed connection, or an initialization timeout.

## 4. Tool list and discovery

The value returned by `tools/list` is the **only** authoritative list. Available tools vary by build, Mono/IL2CPP runtime, current scene, loaded assemblies, security mode, and installed game components. Agents should call `tools/list` at session start, after scene changes, and after security settings change.

Standard MCP methods:

| Method | Purpose | Mutates the game |
|---|---|---:|
| `initialize` | Negotiate protocol version and server capabilities | No |
| `notifications/initialized` | Complete the initialization handshake | No |
| `tools/list` | Fetch names, descriptions, and JSON Schema | No |
| `tools/call` | Invoke a discovered tool | Depends on the tool |

The current tool set:

| Tool | Purpose | Permission |
|---|---|---|
| `get_status` | Read bridge, game, Unity, scene, and capability metadata | Read-only |
| `list_scenes` | List loaded Unity scenes | Read-only |
| `search_objects` | Search by name, path, type, and scene; returns session handles | Read-only |
| `get_object` | Read an object snapshot, members, and Unity object summary | Read-only (getters may still have side effects) |
| `get_member` | Read a field, property, or nested path such as `items[0].value` | Read-only |
| `list_methods` | Enumerate callable methods, signatures, and parameter types | Read-only |
| `set_member` | Set a field, property, or nested member path with JSON-to-CLR conversion | Write; requires read-only off |
| `set_transform` | Set position, rotation, scale, or parent | Write; requires read-only off |
| `set_enabled` | Enable or disable a GameObject or a component exposing `enabled` | Write; requires read-only off |
| `invoke_method` | Invoke an instance or static method with converted arguments | Dangerous; requires read-only off **and** dangerous operations on |
| `create_object` | Create a GameObject, primitive, or add components | Dangerous; requires read-only off **and** dangerous operations on |
| `destroy_object` | Destroy an object, optionally immediately | Dangerous; requires read-only off **and** dangerous operations on |
| `execute_batch` | Run multiple operations in sequence, each independently permission-checked | Depends on the most dangerous sub-operation |

Required arguments per tool: `get_status`, `list_scenes`, `search_objects`, and `create_object` take none; `get_object`, `list_methods`, `set_transform`, and `destroy_object` require `object_id`; `get_member` requires `object_id` and `member_path`; `set_member` requires `object_id`, `member_path`, and `value`; `set_enabled` requires `object_id` and `enabled`; `invoke_method` requires `object_id` and `method`; `execute_batch` requires `operations`.

### 4.1 Permission matrix

| Operation | Read-only on | Read-only off, dangerous off | Read-only off, dangerous on |
|---|---:|---:|---:|
| Status, scenes, search, object/member reads | Allowed | Allowed | Allowed |
| Field/property, Transform, enabled writes | Denied | Allowed | Allowed |
| Method invocation, create, destroy | Denied | Denied | Allowed |
| Batch | Only if every sub-operation is read-only | Read-only and normal writes | All allowed, still checked individually |

MCP annotations are hints for the agent; the real permission check is enforced inside the runtime. Adding a tool to a client allowlist, disabling client-side approval, or wrapping a call in `execute_batch` cannot bypass `MCP_Read_Only` or `MCP_Allow_Dangerous_Operations`.

### 4.2 Batches are not transactions

`execute_batch` runs **ordered and non-atomic**: earlier operations succeed and later ones may fail. `stop_on_error=true` only stops the operations that have not started; it does not undo completed ones. Passing `atomic=true` is rejected, because Unity mutations, method calls, create/destroy, and scene side effects generally cannot be rolled back.

A request timeout does **not** mean the operation did not run. Never automatically retry a batch containing invocation, creation, or destruction.

Suggested agent workflow:

1. Call `tools/list` and only use tools that are actually returned.
2. Narrow the target with query tools first, showing name, type, scene, and a stable identifier.
3. Re-read the target before writing and show the intended difference.
4. Get explicit user approval for destruction, component removal, scene loads, arbitrary reflection calls, and file writes.
5. Re-read after writing to verify; do not blindly retry non-idempotent operations.

## 5. Security settings

### 5.1 Loopback is the enforced boundary

The bridge binds `127.0.0.1` only. It does not bind `0.0.0.0`, LAN addresses, or public addresses, and it rejects non-loopback peers at the socket level. Loopback is not authentication, however: other local processes, browser extensions, and malicious mods in the same user session can still reach the port, so the token is mandatory.

If you genuinely need cross-machine control, keep the bridge on loopback and use an authenticated, encrypted tunnel to map a remote port to the local one. Do not expose the game port directly.

### 5.2 Token

- Generate at least 128 bits of randomness per install or sensitive session; do not use the game name, port, or a short password.
- Use `Authorization: Bearer <token>`; the header name must match the panel configuration.
- Token validation covers the RPC endpoint. The health endpoint can optionally require it too.
- A token must never appear in URLs, command lines, stdout, ordinary logs, crash reports, or version control.
- If you suspect a leak, stop the server, rotate the token, and reconnect clients.

When the token field is empty at startup, the server generates one automatically and writes it back to the configuration.

### 5.3 Read-only mode

With read-only mode on, only pure queries and serialization are allowed. Be aware that even nominally "read" operations can have side effects:

- property getters, `ToString()`, and method calls can execute user code;
- asset, scene, or assembly loads can be triggered lazily;
- lazy collection enumeration, network requests, saves, screenshots, or file exports can be triggered;
- a mutable object obtained through reflection can be written to indirectly.

Read-only enforcement is based on an explicit allowlist in the executor, not on whether a tool name contains `get` or `list`.

### 5.4 Dangerous operations

Two levels are used:

- **Writes allowed**: schema-validated simple field/property and Transform changes that are usually recoverable.
- **Dangerous allowed**: method invocation, object/component destruction, arbitrary type instantiation, static member writes, and anything affecting global game state.

The dangerous switch defaults to off and is **reset to off on every startup**, so authorization never survives a restart. The panel shows the current state. Client-side approval does not imply the user consented to a specific operation; agents should still explain the target, the impact, and how to revert, and ask for confirmation.

## 6. Runtime limitations

### IL2CPP

- Types, generic instances, methods, and metadata that IL2CPP stripped or did not generate wrappers for may be undiscoverable or uncallable.
- Some reflection APIs behave differently than on Mono; argument marshalling, enums, value types, delegates, overload selection, and exception detail may be incomplete.
- A native object may be destroyed while its managed wrapper still looks non-null. Always validate Unity object liveness before and after an operation.
- Do not promise that "anything can be changed". Native plugins, GPU/shader state, anti-cheat protection, and stripped code may be inaccessible.

### Reflection

- Field reads are generally safer than property getters and method calls; a getter or `ToString()` can still change state or hang.
- Overload resolution needs full type information; do not select by method name alone.
- Cyclic object graphs, very large collections, and recursive properties can explode the response; depth, item count, string length, and response size are all capped.
- Static state, singletons, and cross-scene objects have a wider blast radius and should be treated as dangerous.
- UnityExplorer's existing reflection blacklist and crash-avoidance rules still apply; MCP does not bypass them.

### Unity main thread

- UnityEngine APIs are generally not thread-safe. Network threads only parse, authorize, and enqueue; actual reads and writes run on the Unity main thread.
- A paused game, a loading screen, a low frame rate, or a blocked main thread causes timeouts. A client timeout does not prove the operation did not run, and non-idempotent requests must not be retried automatically.
- Per-frame execution is capped. Large edits should be split into batches with verification between steps.
- Scene changes invalidate object handles; rediscover objects afterward.

## 7. Protocol smoke test

The most direct read-only smoke test is to connect a client and complete `initialize`, `tools/list`, then `get_status`. Keep read-only mode on and dangerous operations off throughout.

A minimal check with `curl` (Streamable HTTP mode):

```bash
curl -s http://127.0.0.1:17891/mcp \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
```

Then repeat with `"method":"tools/list"` and with `"method":"tools/call","params":{"name":"get_status","arguments":{}}`.

For SSE, confirm the event-stream handshake returns `200 OK` with `Content-Type: text/event-stream`, then confirm initialization and `tools/list` succeed, and that reconnecting does not deliver responses to the old session.

### Known transport limitation

The HTTP parser requires a `Content-Length` header and **rejects chunked request bodies with `501 Not Implemented`**. Most MCP clients send `Content-Length`, but a client that streams chunked bodies will fail. This is a deliberate scope limit of the built-in transport.

## 8. Troubleshooting

| Symptom | Check |
|---|---|
| `ECONNREFUSED` / cannot connect | Is the game running and MCP enabled? Do the URL, port, and `/mcp` path match the panel? Is a firewall or security product blocking it? |
| HTTP 401/403 | Token or auth header mismatch; stray whitespace in the token; rotate and restart the server after changing it. |
| HTTP 404/405 | Wrong URL/path, or the client transport does not match the panel. SSE mode needs an event-stream `GET`; Streamable HTTP handles `POST` only. |
| HTTP 413 / response too large | Request or response exceeds limits; narrow the query, paginate, or reduce serialization depth rather than raising limits indefinitely. |
| HTTP 429/503 / queue full | Too much concurrency, or the main thread is not pumping. Reduce concurrency; do not run writes concurrently. |
| HTTP 501 | The client sent a chunked request body, which this transport does not support. |
| Timeout, but the game changed afterward | The main thread was loading or stalled. Read back to verify; do not retry non-idempotent calls automatically. |
| `Method not found` / a tool disappeared | Call `tools/list` again; confirm the current build, scene, runtime, and security mode support it. |
| Object not found / stale handle | The object was destroyed or the scene changed. Re-search and confirm by scene, hierarchy path, and type. |
| Works on Mono, fails on IL2CPP | The type may be stripped, the wrapper ungenerated, or the argument unmarshallable. Fall back to simpler field/component APIs. |
| Game stutters | Reduce enumeration scope, depth, and per-frame request count; avoid getters, `ToString()`, and large texture/mesh serialization. |
| Client reports a protocol parse error | Confirm the client transport matches the panel, restart the server, and check the response `Content-Type`, URL, token, and protocol version. |
| Read-only mode still rejects a getter | Expected conservative behavior; getters can have side effects. Use only capabilities explicitly marked read-only. |

When diagnosing, record the UnityExplorer version, loader and version, Mono/IL2CPP, Unity version, active scene, MCP transport mode, security mode, MCP URL (token masked), request `id`, error code, and timestamp. Do not upload saves, tokens, full object dumps, or game logs containing private data.

## 9. Unity 6.3 and later

Unity 6.3 (6000.3) changed `Scene.handle` from `int` to the `SceneHandle` struct. UnityExplorer reads scene handles through a version-agnostic helper, so the MCP tools and the Object Explorer scene list work on both older and newer runtimes. If you are building UnityExplorer from source against a newer Unity, see the `GetSceneIntHandle` / `CreateSceneFromIntHandle` helpers in `UniverseLib.Utility.UnityHelpers`.
